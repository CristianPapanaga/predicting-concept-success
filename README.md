# Predicting Concept Success

*Do behavioural and implicit measures improve concept-screening launch decisions?*

An end-to-end analysis of concept screening: does adding **behavioural** and **implicit**
measures to a survey-only process predict launch success well enough to justify their cost,
and what should a decisive pilot look like?

## What this project demonstrates

- **Data cleaning and missing-data analysis** in `pandas`, splitting *absent by design* values from
  *genuinely missing* ones and running Little's MCAR test.
- **Exploratory analysis** with distributions, correlations, and chi-square tests for how the
  research-package mix shifted over time.
- **Predictive modelling** with `scikit-learn`: linear and ridge regression plus logistic
  regression, standardising predictors to handle collinearity.
- **Model validation**: time-based train/test splits, repeated K-fold cross-validation, and
  ROC-AUC, calibration, and precision-recall diagnostics.
- **Causal caution**: propensity-score weighting for non-random package assignment, plus a
  randomised-pilot recommendation for a causal answer.
- **Cost-benefit and decision-value analysis** with sensitivity checks and cluster-bootstrap
  confidence intervals.
- **Reproducible reporting**: every number and figure is generated by committed code and written to
  Markdown logs, PNG figures, and PowerPoint tables, with a slide deck summarising the result.

Built with `pandas`, `numpy`, `scipy`, `scikit-learn`, `statsmodels`, `pyampute`, `matplotlib`, and
`python-pptx`, managed with `uv`.

## The question

Concept screening today rests mainly on two *stated* survey metrics: **Stated_Appeal** and
**Purchase_Intent**. This project asks whether adding a **behavioural** measure (a simulated
choice task) and an **implicit** measure (an association task) improves launch decisions, and whether
that improvement justifies their cost and time.

## The dataset

A sample dataset of **750 concept tests (2022–2025)** is used throughout. Each row is one concept
test; the columns capture the research package used, the survey/behavioural/implicit metrics, the
pre-launch recommendation, and, for launched concepts, post-launch outcomes such as distribution
and repeat purchase. See `data/data_dictionary.csv` for full field definitions and coding.

## What the analysis found

- **Behavioural is the genuine value-add.** It is the only measure that generalises out of sample
  (test R² **+0.183** vs survey-only **-0.071**; test ROC-AUC **0.669** vs **0.653**), confirmed in
  two independent model families.
- **Implicit is an open question.** Its in-sample gain does not survive out of sample (test R²
  **-0.150**; ROC-AUC **0.550**, at chance) at the small available sample (n = 70).
- **The value hinges on one number.** Behavioural's decision-saving (+€1,494/concept) is real but
  below its +€3,214 premium at equal error-costs; it pays off **if and only if** a stopped winner's
  forgone profit exceeds ~**1.15×** the launch spend (~€85,698).

**Recommendation:** pilot **Behavioural as standard**, test **Implicit on a subset**, and
**randomise** so the next round of evidence is causal.

## AI-first workflow

This project was built end-to-end with an **AI-first workflow**, the way a growing number of
analytics and engineering teams now work. An AI coding assistant drafted every stage (data loading
and cleaning, exploration, modelling, cost-benefit analysis, visualisation, and the written logs),
and **every step was manually reviewed and corrected before being accepted**.

The analysis is structured so the AI's reasoning stays out of the results, which minimises the
opportunity for hallucination:

- **The AI writes code, not conclusions.** Every number, table, and figure is produced by the
  committed `analysis/*.py` scripts running on `data/` and written to `output/`. The assistant's
  job was to write and run that code, so its reasoning is visible, reviewable, and re-runnable
  rather than hidden in a black box.
- **The results are reproducible.** `analysis/exploration.py` and `analysis/modelling.py`
  regenerate the logs and figures from the raw data, so any claim can be traced back to the code
  that produced it.
- **Human verification at every step.** Outputs were checked against the data dictionary and the
  raw data (dtypes, missingness, sample sizes, and the direction and magnitude of every reported
  effect), so errors and hallucinations were caught and fixed before reaching the final output.

The goal is to demonstrate the analysis and the workflow together: using AI to move fast while
keeping a human in the loop and keeping the output fully auditable.

## Repository structure

```
data/                 historical_data.csv + data_dictionary.csv (sample dataset, 750 concept tests, 2022–2025)
analysis/             the analysis code
  data_utilities.py     shared loader / cleaner (single source of truth)
  exploration.py        exploratory data analysis  -> output/logs/exploration.md
  modelling.py          predictive modelling, propensity/IPW, cost-benefit  -> output/logs/modelling.md
  visualisation.py      matplotlib figures  -> output/figures/
  log_writer.py         Markdown logging helper
output/
  logs/                 exploration.md + modelling.md (the supporting analysis file)
  figures/              PNG figures
  tables/               PowerPoint table exports
presentation.pptx      the project deck (slides + speaker notes)
```

## Setup & running

Python **3.11+**, managed with [uv](https://docs.astral.sh/uv/).

```bash
uv sync                                # create/refresh the virtualenv from uv.lock
uv run python analysis/exploration.py  # EDA -> output/logs/exploration.md
uv run python analysis/modelling.py    # modelling + cost-benefit -> output/logs/modelling.md + figures
```

Both scripts resolve the project root from their own path, so they can be run from any directory.
They regenerate their Markdown logs (and, for `modelling.py`, the figures) in `output/`.

## Notes

- The two logs (`exploration.md`, `modelling.md`) together form the supporting analysis file; every
  figure and table in the recommendation traces back to them.
- `python-pptx` is included for exporting tables to PowerPoint (`output/tables/`).
